# Архитектура фронтенд-приложения

Этот документ устанавливает обязательные правила для всех изменений приложения.

## 1. Согласование отклонений

Любое отклонение от архитектуры требует явного согласования с владельцем проекта **до реализации**. Запрос должен содержать нарушаемое правило, причину, затронутые файлы и компоненты, а также объяснение, почему решение в рамках правил не подходит.

Разрешение действует только для согласованного случая и не меняет общее правило. Самостоятельно отключать проверки, добавлять исключения, ослаблять правила или расширять ранее полученное разрешение запрещено.

## 2. View: только отображение

View находится в `<ComponentName>.tsx`. В теле компонента с Presenter разрешены только один безусловный вызов собственного `usePresenter(props)`, получение данных и обработчиков из его результата и возврат JSX.

В JSX разрешены статическая разметка, чтение готовых значений, условия по готовым флагам и `.map()` для отображения готового списка. Внутри `.map()` разрешено создавать JSX элементов; подготовка их данных выполняется в Presenter.

Во View запрещены другие хуки, состояние, эффекты, подписки, запросы, вычисления, форматирование, фильтрация, сортировка, создание обработчиков событий, включая inline-функции, а также чтение хранилищ, контекста, URL и браузерных API.

Например, `disabled={isDisabled}` допустимо; вычисление доступности кнопки выполняется в Presenter.

Для простых компонентов UI kit без Presenter действуют разрешения раздела 6. Это исключение касается только перечисленных там операций; остальные ограничения View сохраняются.

## 3. Presenter: поведение и подготовка данных

Каждый компонент имеет собственный `usePresenter.ts`, кроме простых компонентов UI kit без собственной логики по разделу 6. Presenter принимает props, управляет состоянием и побочными эффектами, получает данные, подготавливает значения для отображения, создаёт обработчики и возвращает готовую модель отображения.

Presenter не возвращает JSX, не импортирует View и не вызывает Presenter другого компонента. При росте его ответственность распределяется между именованными вспомогательными хуками и обычными функциями. Например, `useSuggestion.ts` может быть приватной частью Presenter корзины.

React-хуки вызываются на верхнем уровне компонента или другого хука с соблюдением [Rules of Hooks](https://react.dev/reference/rules/rules-of-hooks).

## 4. Один компонент — одна папка

В папке компонента находятся `<ComponentName>.tsx` и, при необходимости, стили, типы, тесты, вспомогательные модули и локальные дочерние компоненты. Собственный `usePresenter.ts` обязателен, кроме случая, описанного в разделе 6. Определять дополнительные компоненты внутри файла другого компонента запрещено.

Снаружи папки разрешено импортировать только View компонента и его явно выделенные публичные типы. Presenter, вспомогательные файлы и локальные дочерние компоненты являются приватными.

Файловое дерево отражает смысловую структуру интерфейса: страницы, блоки и вложенные элементы. Отдельная папка для каждого DOM-узла не требуется.

## 5. Размещение и область доступности компонентов

Компонент с одним потребителем располагается непосредственно в папке этого потребителя. Компонент с несколькими потребителями располагается в `components` их ближайшего общего предка.

`app/components` содержит прикладные компоненты, общие для приложения. Вложенная `<Owner>/components` доступна самому владельцу и всему его поддереву. Создание `components` определяется областью переиспользования, а не количеством файлов.

Импортировать приватный компонент соседней ветки запрещено. Например, `ProductList` не может напрямую использовать `Cart/AddButton`. Если кнопка нужна и `Cart`, и `ProductList`, её нужно перенести в `Cart/components`.

Если компонент понадобился за пределами поддерева владельца, его нужно перенести в `components` ближайшего общего предка всех потребителей. Поднимать компонент в общую папку «на будущее» запрещено: нужен реальный второй потребитель.

## 6. UI kit без бизнес-логики

`app/ui-kit` содержит переиспользуемые элементы интерфейса: кнопки, поля ввода, списки выбора, диалоги и другие примитивы. Допустимо техническое UI-поведение: фокус, раскрытие списка, клавиатурная навигация.

Запрещены зависимости от бизнес-сущностей, прикладных хранилищ, API приложения и компонентов за пределами `ui-kit`. Например, `Input` знает о значении и событии изменения; поиск товаров и обработка результатов находятся в прикладном компоненте `Search`.

В UI kit Presenter создаётся только при наличии собственной логики компонента. Не создавай Presenter, который только принимает props и возвращает их для передачи в JSX или выполняет перечисленные ниже операции оформления.

Для простого компонента UI kit без Presenter непосредственно во View разрешены:

- деструктуризация props и значения по умолчанию;
- передача HTML-атрибутов, `children` и готовых обработчиков без дополнительных обёрток;
- отображение JSX в зависимости от props;
- выбор оформления из статического набора вариантов и объединение CSS-классов.

Presenter обязателен при использовании React-хуков, состояния, эффектов, подписок, браузерных API, создании собственных обработчиков поведения или вычислениях, выходящих за рамки перечисленных операций оформления. Эта логика размещается в Presenter; View использует готовые значения и обработчики по разделу 2.

Это исключение из требований разделов 2–4 применяется только к простым компонентам UI kit и не требует отдельного согласования. Требования собственной папки, приватности, ограничения размера файлов и запрет бизнес-логики сохраняются.

## 7. Не более 120 строк в файле

Лимит распространяется на исходный код, стили и тесты, включая View, Presenter и вспомогательные модули. Считаются физические строки после форматирования, включая импорты, комментарии и пустые строки.

При превышении лимита файл необходимо разделить по ответственности: самостоятельный фрагмент интерфейса выделить в компонент, поведение — во вспомогательный хук, вычисление или преобразование данных — в именованную функцию.

Уплотнять код, удалять полезное форматирование или механически создавать `part1` / `part2` для обхода ограничения запрещено. Исключения согласуются по общему правилу.

## 8. Границы зависимостей

View импортирует собственный Presenter, если он требуется по разделам 3 и 6, разрешённые дочерние и общие компоненты, UI kit, стили и типы. View простого компонента UI kit без Presenter также может импортировать модули оформления для операций из раздела 6. Presenter импортирует необходимые хуки и модули логики, но не компоненты для отображения. UI kit зависит только от собственных модулей и разрешённых внешних библиотек.

Циклические зависимости запрещены. Реэкспорты и алиасы не дают права обходить ограничения доступа.

## Пример структуры

```text
app/
├── App.tsx
├── usePresenter.ts
├── ui-kit/
│   ├── Button/
│   │   ├── Button.tsx
│   │   └── types.ts
│   ├── Input/
│   │   ├── Input.tsx
│   │   └── usePresenter.ts
│   └── Select/
│       ├── Select.tsx
│       └── usePresenter.ts
├── components/
│   └── Search/
│       ├── Search.tsx
│       └── usePresenter.ts
├── Cart/
│   ├── Cart.tsx
│   ├── usePresenter.ts
│   ├── useSuggestion.ts
│   ├── AddButton/
│   │   ├── AddButton.tsx
│   │   └── usePresenter.ts
│   ├── ProductList/
│   │   ├── ProductList.tsx
│   │   ├── usePresenter.ts
│   │   └── style.module.css
│   └── components/
│       └── Price/
│           ├── Price.tsx
│           └── usePresenter.ts
└── Settings/
    ├── Settings.tsx
    └── usePresenter.ts
```

В этом примере `Button` — простой компонент UI kit без Presenter по разделу 6. `Search` используется в нескольких ветках приложения. `Price` доступен самому `Cart`, `AddButton` и `ProductList`, но недоступен `Settings`.

## Обязательные проверки

По решению владельца проекта соответствие этому документу агент проверяет самостоятельно вручную перед завершением каждой задачи. Обязательны проверка лимита 120 физических строк после форматирования, ограничений View, собственной папки каждого компонента, наличия Presenter там, где он требуется, и соблюдения условий исключения для простого UI kit по разделу 6. Также проверяются приватность, области доступности и отсутствие циклических зависимостей.

В это же ревью входят отсутствие бизнес-логики в UI kit, соответствие ответственности слоёв и осмысленность декомпозиции. Нарушения необходимо исправить до завершения работы; отклонения согласуются по разделу 1.

Автоматические проверки проекта — Biome и TypeScript/сборка Vite (`npm run check`). Они не заменяют ручное архитектурное ревью.
