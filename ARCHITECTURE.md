# Архитектура фронтенд-приложения

Этот документ устанавливает обязательные правила организации кода,
размещения файлов и взаимодействия архитектурных слоёв приложения.
Правила распространяются на все новые изменения и рефакторинг.

Основные принципы: явные границы ответственности, один владелец
состояния, ограниченная область доступности модулей, независимость
бизнес-сценариев от React и предсказуемое направление зависимостей.

Имена директорий `logic` и `tasks` всегда пишутся в нижнем регистре,
как в локальных папках компонентов, так и в общей папке `app/tasks`.

## 1. Согласование отклонений

Любое отклонение от архитектуры требует явного согласования с владельцем
проекта **до реализации**. Запрос должен содержать нарушаемое правило,
причину, затронутые файлы и компоненты, а также объяснение, почему
решение в рамках правил не подходит.

Разрешение действует только для согласованного случая и не меняет общее
правило. Самостоятельно отключать проверки, добавлять исключения,
ослаблять правила или расширять ранее полученное разрешение запрещено.

## 2. View: только отображение

View находится в `<ComponentName>.tsx`. Если компоненту нужен Presenter,
в теле View разрешены только один безусловный вызов собственного
`usePresenter(props)`, получение данных и обработчиков из его результата
и возврат JSX либо `null`. Компонент без логики использует готовые
значения и обработчики из props без `usePresenter`.

В JSX разрешены статическая разметка, чтение готовых значений, условия
по готовым флагам и `.map()` для отображения готового списка. Внутри
`.map()` разрешено создавать JSX-элементы; подготовка их данных
выполняется в Presenter.

Ранний выход `if (!isVisible) return null;` разрешён по готовому флагу
из Presenter или props. Если используется `usePresenter`, ранний выход
выполняется после его безусловного вызова. Само условие видимости
вычисляется вне View.

Во View запрещены другие хуки, состояние, эффекты, подписки, запросы,
вычисления, форматирование, фильтрация, сортировка, создание
обработчиков событий, включая inline-функции, а также чтение хранилищ,
контекста, URL и браузерных API.

Например, `disabled={isDisabled}` допустимо; вычисление доступности
кнопки выполняется в Presenter.

## 3. Presenter: управление интерфейсом и координация

Presenter находится в `logic/usePresenter.ts` внутри папки своего
компонента. Папка `logic` содержит логику, принадлежащую этому
компоненту: Presenter, вспомогательные хуки, функции и локальные Tasks.

Presenter принимает props, управляет UI-состоянием и UI-эффектами,
получает данные для отображения, подготавливает модель представления,
создаёт обработчики и возвращает готовые значения для View.

Presenter отвечает за: - состояние интерфейса: `loading`, `error`,
`isOpen`, выбранные вкладки и другие локальные UI-состояния; - обработку
событий интерфейса и вызов соответствующих Tasks; - подписку на Store
через предусмотренные проектом React-хуки и селекторы; - подготовку,
форматирование и преобразование данных для View; - обработку результата
выполнения Tasks и преобразование ошибок в состояние интерфейса; -
навигацию и другие действия, зависящие от среды исполнения приложения.

Presenter не должен содержать полноценные пользовательские сценарии,
последовательности бизнес-операций или прямую реализацию запросов к API.
Такие сценарии выносятся в Tasks. Presenter может вызывать Task при
событии пользователя или из эффекта, если это необходимо для сценария
загрузки данных.

Presenter не возвращает JSX, не импортирует View и не вызывает Presenter
другого компонента. При росте его ответственности она распределяется
между именованными вспомогательными хуками и обычными функциями.
Например, `logic/useSuggestion.ts` может быть приватной частью Presenter
корзины.

Компоненту без логики Presenter не нужен; пустой `logic/usePresenter.ts`
не создаём.

React-хуки вызываются на верхнем уровне компонента или другого хука с
соблюдением [Rules of
Hooks](https://react.dev/reference/rules/rules-of-hooks).

## 4. Tasks: пользовательские сценарии и бизнес-логика

Task --- это самостоятельный сценарий использования приложения (Use
Case), реализованный обычной JavaScript/TypeScript-функцией. Она
описывает действие, которое пользователь просит выполнить у системы, и
необходимые для этого операции.

Примеры: - `login` --- авторизация пользователя; - `logout` --- выход из
аккаунта; - `addProduct` --- добавление товара; - `removeProduct` ---
удаление товара; - `createOrder` --- создание заказа; - `uploadFile` ---
загрузка файла; - `loadProducts` --- получение списка товаров.

Основные правила:

1.  Одна Task представляет один самостоятельный сценарий использования и
    имеет одно основное действие.
2.  Название Task начинается с глагола и описывает действие.
3.  Task --- обычная синхронная или асинхронная функция, а не
    React-компонент, хук или специальный middleware.
4.  Входные данные передаются через аргументы функции. Результат
    выполнения возвращается вызывающему коду.
5.  Task может вызывать другие Tasks и вспомогательные функции, если это
    помогает переиспользовать самостоятельные операции и сохраняет
    понятный сценарий.
6.  Task может координировать несколько операций: обращаться к сервисам,
    API и Store, выполнять необходимые проверки и организовывать
    последовательность действий.
7.  Task не содержит JSX, не импортирует React и не использует React
    Hooks.
8.  Task не импортирует View, Presenter и локальные UI-компоненты.
9.  Task не управляет UI-состоянием: `loading`, открытием диалогов,
    отображением уведомлений и текстов ошибок.
10. Task не выполняет навигацию. Навигация находится в Presenter,
    поскольку может зависеть от платформы и используемого роутера.
11. Task не должна напрямую зависеть от конкретной реализации интерфейса
    или способа отображения данных.
12. Чистые бизнес-правила и вычисления, которые могут использоваться в
    разных сценариях, выносятся в отдельные именованные функции или
    доменные модули.

Бизнес-правила описывают правила предметной области и могут существовать
независимо от приложения. Use Case описывает сценарий, который
приложение выполняет для пользователя. В проекте прикладные сценарии
реализуются через Tasks, а устойчивые правила предметной области не
следует дублировать в Presenter или View.

Task должна оставаться независимой от React. Её можно вызывать из разных
частей приложения и тестировать без рендеринга компонентов.

### Результаты и ошибки

Task возвращает данные или результат, необходимый вызывающему коду.
Ошибки выполнения передаются вызывающему коду через исключение (`throw`)
либо через принятый в проекте единый тип результата. В рамках одного
проекта необходимо придерживаться одного согласованного подхода.

Task не должна самостоятельно формировать пользовательские сообщения об
ошибках. Presenter отвечает за преобразование ошибки в состояние и
представление, подходящее для интерфейса. Перехватывать ошибку внутри
Task следует только тогда, когда Task может корректно обработать её,
восстановиться или преобразовать на границе своей ответственности.

## 5. Размещение и область доступности Tasks

Расположение Task определяется тем, сколько компонентов её используют.

**Локальная Task** используется только одним компонентом и находится в
`logic/tasks/` этого компонента.

**Общая Task** используется несколькими компонентами и размещается в
глобальной папке `app/tasks/`. Не нужно создавать промежуточные общие
папки `tasks` внутри веток компонентов: переиспользуемые сценарии
находятся в одном общем месте.

Примеры: - `Cart/logic/tasks/addProduct.ts` --- сценарий, используемый
только компонентом `Cart`; - `Cart/logic/tasks/removeProduct.ts` ---
сценарий, используемый только компонентом `Cart`; -
`app/tasks/logout.ts` --- сценарий, используемый несколькими
независимыми компонентами.

Если Task содержит несколько вспомогательных файлов или превышает лимит
строк, для неё создаётся отдельная подпапка внутри `tasks` с главным
файлом и приватными модулями. Простую Task достаточно хранить в одном
файле.

Не поднимать Task в общую папку «на будущее»: перенос выполняется при
появлении реального второго потребителя. Приватные локальные Tasks не
импортируются за пределами своего компонента.

## 6. Взаимодействие Tasks с API, сервисами и Store

Tasks координируют выполнение пользовательских сценариев и могут
обращаться к API, сервисам, доменным функциям и Store через
предусмотренные проектом публичные интерфейсы.

Для взаимодействия с API Task использует сервисы или API-модули, а не
реализует транспортные детали внутри сценария. Формирование
HTTP-запросов, заголовков, токенов, сериализация и детали протокола
относятся к API-слою.

Если сценарий требует работы с браузерными или платформенными
возможностями (например, Push API, Service Worker или локальным
хранилищем), Task использует соответствующий сервис. Прямые зависимости
от React и UI при этом не допускаются.

### Работа со Store

Tasks могут изменять общее состояние приложения через публичный API
Store. Для этого не используются React Hooks: Task должна работать вне
React-компонента.

Допустимые способы зависят от выбранного State Manager: - Redux: импорт
экземпляра Store и использование публичных методов `dispatch` и
`getState`; - Zustand: использование публичных методов Store, включая
`getState` и `setState`; - MobX: использование публичных методов и
actions соответствующего Store.

Прямой импорт экземпляра Store в Task допустим, если это принято
архитектурой проекта. Task должна использовать только публичный API
Store и не обращаться к его внутренним деталям.

При таком подходе Task зависит от выбранного State Manager. Если проект
переходит с Redux на Zustand или MobX, места прямого обращения к Store
необходимо изменить вместе с реализацией хранилища. Не следует
одновременно утверждать, что такая Task полностью независима от State
Manager.

Не следует вводить Redux Thunk, Redux Saga или другие посредники только
ради возможности выполнить обычную Task, если проектный Store уже
предоставляет подходящий публичный API. Это правило не запрещает
существующие middleware и инструменты, когда они решают отдельную
необходимую задачу.

### Пример: Task выхода из аккаунта с Redux

Task остаётся обычной функцией. Она вызывает сервисы и напрямую
использует публичный API Store:

```ts
// app/tasks/logout/logout.ts

import { store } from '@/app/store'
import { clearUser } from '@/app/store/userSlice'
import { clearChats } from '@/app/store/chatSlice'
import { authApi } from '@/app/services/authApi'
import { pushService } from '@/app/services/pushService'

export async function logout(): Promise<void> {
  await pushService.unsubscribe()
  await authApi.logout()

  store.dispatch(clearUser())
  store.dispatch(clearChats())
}
```

Presenter вызывает Task и отвечает за состояние интерфейса и навигацию:

```ts
// app/Account/logic/usePresenter.ts

import { useState } from 'react'
import { useNavigate } from 'react-router-dom'
import { logout } from '@/app/tasks/logout/logout'

export function usePresenter() {
  const [loading, setLoading] = useState(false)
  const [error, setError] = useState<string | null>(null)
  const navigate = useNavigate()

  const onLogout = async () => {
    setLoading(true)
    setError(null)

    try {
      await logout()
      navigate('/login')
    } catch {
      setError('Не удалось выйти из аккаунта')
    } finally {
      setLoading(false)
    }
  }

  return { loading, error, onLogout }
}
```

В этом примере Task знает о публичном API Redux Store, но не зависит от
React. Presenter не знает, какие именно Redux actions очищают
пользовательские данные: он только вызывает сценарий `logout` и
обрабатывает его результат.

Порядок операций в примере иллюстративный. Если отписка от Push должна
быть необязательной или не должна блокировать выход, это поведение явно
реализуется согласно требованиям продукта.

## 7. Навигация и платформенные действия

Навигация выполняется в Presenter или в механизме навигации, который
принадлежит слою представления. Tasks не импортируют роутер и не
выполняют переходы между страницами.

Причина: один и тот же пользовательский сценарий может выполняться в
разных средах, а поведение навигации в браузере и мобильном приложении
может различаться. Task сообщает об успешном или неуспешном результате;
Presenter определяет, что делать с интерфейсом после этого результата.

То же правило применяется к другим действиям, зависящим от UI или
платформы: Task вызывает абстракцию сервиса, а Presenter управляет
UI-реакцией.

## 8. Один компонент --- одна папка

В папке компонента находятся `<ComponentName>.tsx` и папка `logic/`,
если компоненту нужна логика. В `logic/` размещаются: -
`usePresenter.ts` --- Presenter компонента; - вспомогательные хуки и
функции, используемые только этим компонентом; - `tasks/` --- локальные
пользовательские сценарии, если они есть.

При необходимости в папке компонента также располагаются стили,
публичные типы и тесты. Компонент без логики не требует папки `logic/`.

Размещать несколько компонентов в одной папке запрещено: каждый
локальный дочерний компонент должен находиться в собственной подпапке.
Определять дополнительные компоненты внутри файла другого компонента
запрещено.

Снаружи папки разрешено импортировать только View компонента и его явно
выделенные публичные типы. Папка `logic/`, Presenter, локальные Tasks и
вспомогательные файлы являются приватными.

Файловое дерево отражает смысловую структуру интерфейса: страницы, блоки
и вложенные элементы. Отдельная папка для каждого DOM-узла не требуется.

## 9. Размещение и область доступности компонентов

Компонент с одним потребителем располагается в собственной подпапке
папки этого потребителя. Компонент с несколькими потребителями
располагается в собственной подпапке `components` их ближайшего общего
предка.

`app/components` содержит прикладные компоненты, общие для приложения.
Вложенная `<Owner>/components` доступна самому владельцу и всему его
поддереву. Создание `components` определяется областью
переиспользования, а не количеством файлов.

Импортировать приватный компонент соседней ветки запрещено. Например,
`ProductList` не может напрямую использовать `Cart/AddButton`. Если
кнопка нужна и `Cart`, и `ProductList`, её нужно перенести в
`Cart/components`.

Если компонент понадобился за пределами поддерева владельца, его нужно
перенести в `components` ближайшего общего предка всех потребителей.
Поднимать компонент в общую папку «на будущее» запрещено: нужен реальный
второй потребитель.

## 10. Один владелец состояния

Состояние располагается у ближайшего общего предка компонентов, которым
оно необходимо. Данные передаются вниз через props, изменения --- через
обработчики. Родительский и дочерний Presenter не обращаются к
внутреннему состоянию друг друга.

Необходимо различать:

-   **UI-состояние** --- состояние конкретного интерфейса: `loading`,
    `error`, открытие диалога, выбранная вкладка. Оно принадлежит
    соответствующему Presenter, если не требуется нескольким
    компонентам.
-   **Общее состояние приложения** --- данные, используемые разными
    частями приложения: текущий пользователь, корзина, чаты и другие
    общие данные. Они принадлежат Store или другому единому владельцу
    состояния.

Tasks могут инициировать изменение общего состояния через публичный API
Store. Они не должны создавать параллельные копии общего состояния.
Presenter может читать Store через предусмотренные проектом хуки и
селекторы, чтобы подготовить данные для View.

Повторный вызов одного хука в разных компонентах не создаёт общее
состояние: хуки переиспользуют логику, а каждый вызов имеет собственное
состояние. Подробнее --- в [документации
React](https://react.dev/learn/reusing-logic-with-custom-hooks).

## 11. UI kit без бизнес-логики

`app/ui-kit` содержит переиспользуемые элементы интерфейса: кнопки, поля
ввода, списки выбора, диалоги и другие примитивы. Допустимо техническое
UI-поведение: фокус, раскрытие списка, клавиатурная навигация.

Запрещены зависимости от бизнес-сущностей, прикладных хранилищ, API
приложения, Tasks и компонентов за пределами `ui-kit`. Например, `Input`
знает о значении и событии изменения; поиск товаров и обработка
результатов находятся в прикладном компоненте `Search`.

Правила разделения View и Presenter и собственной папки действуют и для
`ui-kit`. Presenter нужен только при наличии логики; компонентам без
логики он не требуется.

## 12. Не более 120 строк в файле

Лимит распространяется на исходный код, стили и тесты, включая View,
Presenter, Tasks и вспомогательные модули. Считаются физические строки
после форматирования, включая имконтракты зависимостей, комментарии и
пустые строки.

При превышении лимита файл необходимо разделить по ответственности: -
самостоятельный фрагмент интерфейса выделить в компонент; - поведение
интерфейса --- во вспомогательный хук; - самостоятельный
пользовательский сценарий --- в Task; - вычисление или преобразование
данных --- в именованную функцию; - детали API, интеграции или платформы
--- в соответствующий сервис.

Уплотнять код, удалять полезное форматирование или механически создавать
`part1` / `part2` для обхода ограничения запрещено. Исключения
согласуются по общему правилу.

## 13. Границы зависимостей

Допустимое направление зависимостей:

-   **View** импортирует собственный `logic/usePresenter.ts` при его
    наличии, разрешённые дочерние и общие компоненты, UI kit, стили и
    типы.
-   **Presenter** находится в `logic/`, использует React-хуки и
    селекторы, подготавливает модель представления и вызывает локальные
    или глобальные Tasks. Он не импортирует View другого компонента и не
    содержит реализации бизнес-сценариев.
-   **Локальные Tasks** находятся в `Component/logic/tasks/` и доступны
    только этому компоненту.
-   **Общие Tasks** находятся в `app/tasks/` и могут использоваться
    разными компонентами.
-   **Tasks** используют доменные функции, сервисы, API-модули и
    публичный API Store. Они не импортируют React, View, Presenter, UI
    kit или роутер.
-   **Services / API** инкапсулируют интеграции, транспорт и
    платформенные детали. Они не зависят от View и Presenter.
-   **UI kit** зависит только от собственных модулей и разрешённых
    внешних библиотек. Он не зависит от прикладных Tasks, Store и API
    приложения.

Папка `logic/` приватна для своего компонента. Её содержимое не
импортируется соседними компонентами. Для повторного использования
логики необходимо выделить самостоятельный модуль в соответствующую
общую область: общую Task --- в `app/tasks/`, общий компонент --- в
`components` ближайшего общего предка, сервис --- в соответствующую
общую папку приложения.

Циклические зависимости запрещены. Реэксконтракты зависимостей и алиасы
не дают права обходить ограничения доступа.

## Обязательные проверки

Проверки должны блокировать слияние изменений:

1.  **Лимит строк** --- ESLint
    [`max-lines`](https://eslint.org/docs/latest/rules/max-lines) для
    TS/TSX и отдельная проверка остальных файлов.
2.  **Ограничения View** --- правило ESLint с анализом AST: разрешён
    только собственный `usePresenter` и предусмотренная структура
    возврата JSX.
3.  **Структура компонентов** --- проверка наличия отдельной папки
    компонента, размещения `usePresenter.ts` и локальных хуков внутри
    `logic/`, допустимых файлов и отсутствия пустого Presenter у
    компонентов без логики.
4.  **Границы Tasks** --- проверка, что Tasks не импортируют React,
    View, Presenter, UI kit и роутер; проверка размещения локальных
    Tasks в `logic/tasks/` и допустимых областей импорта общих Tasks.
5.  **Приватность и области доступности** --- проверка графа импортов
    для компонентов, папок `logic/`, Tasks и вспомогательных модулей.
6.  **Циклические зависимости** --- автоматическая проверка графа
    импортов.
7.  **Соглашение об именовании Tasks** --- проверка именования
    экспортируемых сценариев глаголами там, где это возможно
    автоматизировать.

Отсутствие бизнес-логики в UI kit, соответствие ответственности слоёв,
корректность границ пользовательских сценариев, осмысленность
декомпозиции и корректность использования публичного API Store
дополнительно проверяются на архитектурном ревью. Автоматические
проверки не заменяют эту проверку.
