# SA — инструкции для AI-агентов

Эти инструкции действуют для всего проекта и всех задач, включая исправления, рефакторинг, тесты и изменения конфигурации.

## Обязательный источник правил

Перед планированием и любыми изменениями полностью прочитай актуальный [ARCHITECTURE.md](./ARCHITECTURE.md). Все изменения должны соответствовать ему, даже если пользователь не упоминает архитектуру в задаче. При ревью также используй этот документ как критерий проверки.

`ARCHITECTURE.md` — источник истины. Краткие памятки, существующий код и предыдущие реализации не заменяют его и не разрешают отступать от правил. Если документ недоступен, не начинай зависящие от него изменения и сообщи о проблеме.

Передавая работу другому агенту, явно включай обязательное чтение этого документа и соблюдение его требований в поручение.

## Работа над изменениями

1. До реализации определи размещение компонентов, границы View/Presenter/Tasks и публичные импорты по `ARCHITECTURE.md`. Работу с состоянием организуй по разделу 10 архитектуры и уточнениям этого файла.
2. View с логикой вызывает собственный `logic/usePresenter.ts` и возвращает JSX. Чистый компонент, которому достаточно прямой передачи props в JSX, может обходиться без Presenter. Вычисления, выбор вариантов оформления и обработчики готовь в Presenter; не создавай пустой Presenter только для прогона props. Приватные хуки, функции и локальные Tasks размещай внутри собственного `logic/`.
3. После форматирования проверяй лимит 120 физических строк для исходного кода, стилей и тестов. Декомпозируй по ответственности, не обходи лимит уплотнением кода.
4. Перед завершением проверь изменённые файлы и затронутые зависимости по всем разделам архитектуры, включая отсутствие циклов. Существующее нарушение не является разрешением повторять его.

Имена директорий `logic` и `tasks` всегда пишутся в нижнем регистре.

## Стиль функций

Все функции в проекте пиши стрелочными через `const`: компоненты, Presenter, хуки, обработчики и вспомогательные функции. Используй `const name = (...) => { ... }`, для асинхронных функций — `const name = async (...) => { ... }`. Не используй объявления и выражения с ключевым словом `function`.

Для именованного экспорта используй `export const name = ...`; для экспорта компонента по умолчанию сначала объяви `const Component = ...`, затем `export default Component`. Разделение View/Presenter и правила вызова хуков сохраняются.

Вложенные тернарные выражения запрещены правилом Biome `style.noNestedTernary` с уровнем `error`. Используй `if` с ранними возвратами или именованные вспомогательные функции.

## Tasks и зависимости

Бизнес-сценарии выполняют обычные стрелочные функции Tasks с именами-глаголами. Task одного компонента находится в его `logic/tasks`, общий сценарий — в `src/app/tasks`. Не создавай Task для простого вызова setter, dispatch или обработки DOM-события. Tasks не зависят от React, View, Presenter и навигации; транспорт находится в `src/app/services`.

Поиск выполняет `src/app/tasks/loadShows.ts`: нормализует входной запрос, получает данные через API-сервис, преобразует ответ и убирает дубликаты. Это общий сценарий для поиска из SearchField, повтора из Feedback и восстановления ссылки; единый вызов через middleware не делает его локальным для одного компонента. Middleware вызывает Task, сохраняя отдельную ответственность за debounce, отмену и защиту от устаревших ответов. Не добавляй новый middleware или thunk только ради запуска Task.

Сервисы возвращают технические ошибки, Redux хранит сериализуемый код ошибки, а пользовательские сообщения готовит Presenter. Не переноси UI-тексты и навигацию в Tasks или API.

## Состояние

Прикладное состояние поиска хранится в Redux Toolkit: строка запроса, выбранный жанр, страница, результаты, статус загрузки и ошибка. Не дублируй эти данные в локальном React state. Прикладные Presenter читают нужные данные напрямую через типизированные хуки и селекторы Redux, а изменения отправляют через actions. Не передавай данные и обработчики Redux через промежуточные компоненты, которым они не нужны.

Подписывай Presenter только на используемые значения; общие производные данные вычисляй мемоизированными селекторами. Несколько подписок читают один store и не создают копий состояния. Не импортируй singleton store в Presenter. View и UI kit не обращаются к Redux; UI kit и компоненты, которым достаточно входных данных (например, `ShowCard`), получают props от непосредственного потребителя.

URL с параметрами `q`, `genre` и `page` сериализует поисковое состояние Redux. Прямую ссылку и переходы «Назад» / «Вперёд» восстанавливай атомарно через Redux, без отдельной локальной копии параметров. Браузерный bootstrap и механизм навигации в `src/app/navigation` могут читать URL и работать с History API; View и Tasks не читают URL, не вызывают браузерные API и не управляют историей.

Сохраняй посторонние параметры URL и hash. Нормализуй жанр и границы страницы по результатам только после успешного поиска; во время загрузки или ошибки не теряй значения из ссылки. Восстановление `popstate` и нормализация URL не должны создавать новые шаги истории.

Статус запроса и код ошибки разделяют App, Results и Feedback, поэтому они также принадлежат Redux. Производные списки, жанры и количество страниц вычисляй из исходного состояния, не сохраняй их отдельными копиями. Изолированное техническое UI-состояние и поведение остаются локальными в Presenter: refs и фокус поля, `useId`, ошибка загрузки постера. Таймеры, `AbortController` и Promise не помещай в Redux state.

## Стили

Используй только стандартные utility-классы, палитру, размеры, типографику, анимации и брейкпоинты Tailwind CSS. Произвольные значения и варианты в квадратных скобках запрещены; не переноси их в CSS, inline-стили или собственные переменные темы для обхода этого правила. Базовые стили находятся в `src/index.css` (`@layer base`). Статические классы задавай во View; выбор вариантов и объединение классов выполняй в собственном Presenter. Это правило действует и для UI kit по разделу 11 архитектуры. Используй полные литеральные имена классов, чтобы Tailwind обнаруживал их при сборке; не собирай имена из динамических фрагментов.

В Biome включён `nursery.noTailwindArbitraryValue: error`. Все литеральные определения классов вне JSX, включая константы и значения словаря вариантов, оборачивай в `tw(...)` из `src/app/ui-kit/tw.ts`: Biome распознаёт этот вызов и проверяет строки. Одного `tw(variable)` недостаточно для проверки исходного литерала. Во View передавай готовые классы без вызова `tw`. Это соглашение проекта, а не требование архитектуры к способу оформления.

Встроенное правило не проверяет произвольные варианты и модификаторы; их запрет остаётся обязательной частью ручного ревью.

## Отклонения

Следуй процедуре согласования из раздела 1 `ARCHITECTURE.md`: явное разрешение владельца проекта требуется до реализации отклонения. Запрос должен назвать нарушаемое правило, причину, затронутые файлы и компоненты и объяснить, почему решение в рамках правил не подходит.

Разрешение действует только для согласованного случая. Не ослабляй архитектуру, не отключай проверки, не добавляй исключения и не расширяй разрешение самостоятельно, в том числе через правки этого файла или `ARCHITECTURE.md`.

## Проверка результата

- `npm run lint` — Biome: код, форматирование и импорты.
- `npm run lint:architecture` — ESLint/AST и граф модулей: View, хуки, лимит строк, структура, приватность, Tasks, зависимости и циклы.
- `npm run build` — TypeScript и production-сборка Vite.
- `npm run check` — Biome, автоматическая проверка архитектуры и сборка; выполняй после изменений приложения. Эта же команда запускается в GitHub Actions для pull request и перед публикацией.
- Обязательные автоматические проверки из обновлённого `ARCHITECTURE.md` находятся в `eslint.config.mjs` и `tooling/architecture`. Они дополняют ручное ревью, а не заменяют его. Не добавляй исключения, отключения правил и обходы проверок без согласованного отклонения.
- При каждой задаче вручную проверь все применимые разделы архитектуры, содержательность Presenter/Tasks, область переиспользования и единственного владельца состояния. Если часть проверки не выполнена, прямо укажи это в результате.
