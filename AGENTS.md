# SA — инструкции для AI-агентов

Эти инструкции действуют для всего проекта и всех задач, включая исправления, рефакторинг, тесты и изменения конфигурации.

## Обязательный источник правил

Перед планированием и любыми изменениями полностью прочитай актуальный [ARCHITECTURE.md](./ARCHITECTURE.md). Все изменения должны соответствовать ему, даже если пользователь не упоминает архитектуру в задаче. При ревью также используй этот документ как критерий проверки.

`ARCHITECTURE.md` — источник истины. Краткие памятки, существующий код и предыдущие реализации не заменяют его и не разрешают отступать от правил. Если документ недоступен, не начинай зависящие от него изменения и сообщи о проблеме.

Передавая работу другому агенту, явно включай обязательное чтение этого документа и соблюдение его требований в поручение.

## Работа над изменениями

1. До реализации определи размещение компонентов, границы View/Presenter, публичные импорты и владельца состояния по `ARCHITECTURE.md`.
2. Соблюдай все правила документа, включая требования к Presenter с исключением для простого UI kit по разделу 7, приватность модулей, область переиспользования компонентов и ограничения UI kit. В таком UI kit не создавай формальный Presenter только для передачи props, значений по умолчанию и подготовки оформления.
3. После форматирования проверяй лимит 120 физических строк для исходного кода, стилей и тестов. Декомпозируй по ответственности, не обходи лимит уплотнением кода.
4. Перед завершением проверь изменённые файлы и затронутые зависимости по всем разделам архитектуры, включая отсутствие циклов. Существующее нарушение не является разрешением повторять его.

## Стиль функций

Все функции в проекте пиши стрелочными через `const`: компоненты, Presenter, хуки, обработчики и вспомогательные функции. Используй `const name = (...) => { ... }`, для асинхронных функций — `const name = async (...) => { ... }`. Не используй объявления и выражения с ключевым словом `function`.

Для именованного экспорта используй `export const name = ...`; для экспорта компонента по умолчанию сначала объяви `const Component = ...`, затем `export default Component`. Разделение View/Presenter и правила вызова хуков сохраняются.

Вложенные тернарные выражения запрещены правилом Biome `style.noNestedTernary` с уровнем `error`. Используй `if` с ранними возвратами или именованные вспомогательные функции.

## Состояние

Прикладное состояние поиска хранится в Redux Toolkit: строка запроса, выбранный жанр, страница, результаты, статус загрузки и ошибка. Не дублируй эти данные в локальном React state. Единственная UI-точка чтения и изменения этого состояния — Presenter приложения; дочерние компоненты получают данные через props и передают изменения через callbacks.

Жизненным циклом запросов управляет middleware хранилища: debounce, отмена предыдущего запроса и защита от устаревших ответов. Производные списки, жанры и количество страниц вычисляй из исходного состояния, не сохраняй их отдельными копиями. Изолированное техническое UI-состояние и поведение остаются локальными: refs и фокус поля, `useId`, ошибка загрузки постера. Таймеры, `AbortController` и Promise не помещай в Redux state.

## Стили

Используй только стандартные utility-классы, палитру, размеры, типографику, анимации и брейкпоинты Tailwind CSS. Произвольные значения и варианты в квадратных скобках запрещены; не переноси их в CSS, inline-стили или собственные переменные темы для обхода этого правила. Базовые стили находятся в `src/index.css` (`@layer base`). Статические классы задавай во View; условные наборы классов подготавливай в собственном Presenter. Для простого UI kit без Presenter разрешены выбор вариантов оформления и объединение классов во View по разделу 7 `ARCHITECTURE.md`. Используй полные литеральные имена классов, чтобы Tailwind обнаруживал их при сборке; не собирай имена из динамических фрагментов.

В Biome включён `nursery.noTailwindArbitraryValue: error`. Все литеральные определения классов вне JSX, включая константы и значения словаря вариантов, оборачивай в `tw(...)` из `src/app/ui-kit/tw.ts`: Biome распознаёт этот вызов и проверяет строки. Одного `tw(variable)` недостаточно для проверки исходного литерала. Во View компонентов с Presenter передавай готовые классы без вызова `tw`. Во View простого UI kit без Presenter допускается `tw` для объединения классов. Это соглашение проекта, а не требование архитектуры к способу оформления.

Встроенное правило не проверяет произвольные варианты и модификаторы; их запрет остаётся обязательной частью ручного ревью.

## Отклонения

Следуй процедуре согласования из раздела 1 `ARCHITECTURE.md`: явное разрешение владельца проекта требуется до реализации отклонения. Запрос должен назвать нарушаемое правило, причину, затронутые файлы и компоненты и объяснить, почему решение в рамках правил не подходит.

Разрешение действует только для согласованного случая. Не ослабляй архитектуру, не отключай проверки, не добавляй исключения и не расширяй разрешение самостоятельно, в том числе через правки этого файла или `ARCHITECTURE.md`.

## Проверка результата

- `npm run lint` — Biome: код, форматирование и импорты.
- `npm run build` — TypeScript и production-сборка Vite.
- `npm run check` — Biome и сборка; выполняй после изменений приложения.
- По прямому указанию владельца проекта соответствие `ARCHITECTURE.md` агент проверяет самостоятельно вручную при каждой задаче: View/Presenter с учётом условий исключения для простого UI kit по разделу 7, структуру, приватность и области доступности, владельца состояния, UI kit, циклы, декомпозицию и лимит 120 строк после форматирования.
- Biome и успешная сборка не заменяют ручное архитектурное ревью. Если часть проверки не выполнена, прямо укажи это в результате и не заявляй, что полное соответствие архитектуре подтверждено.
